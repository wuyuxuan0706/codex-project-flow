## Codex 应用验收

| ID | 场景 | 预期结果 |
| --- | --- | --- |
| C-01 | 普通请求确认 | 中枢先给出理解和执行项；未确认零创建，确认后只创建一个可见执行任务 |
| C-02 | 中枢初始移交 | 执行任务身份建立后，中枢不再接收该请求的后续消息或管理动作 |
| C-03 | 子任务修改确认 | 范围变化由原任务输出新的理解和执行项；确认后任务 ID、`requestId` 和 generation 不变 |
| C-04 | 文档先审后写 | 原任务先输出完整纯文本草稿；否决时零 Markdown 写入，精确批准后才写入，后续再改须重新评审 |
| C-05 | 完成否决 | 用户否决后原任务直接进入修改确认循环，不返回中枢或创建新任务 |
| C-06 | 子任务完整生命周期 | 范围修改、文档评审、执行、验证和完成验收全部在同一执行任务中完成 |
| C-07 | 自归档 | 用户最终同意后执行任务自行归档；只有精确归档成功才结束请求 |
| C-08 | 活动任务与排队 | 活动、queued 或等待验收任务继续占位；名额明确释放前不同目标不物化 |
| C-09 | 升级连续性 | 同一升级请求保持任务身份；范围确认、文档评审、空快照检查、屏障、验收和自归档都留在升级任务 |
| C-10 | 插件缓存 | 新任务加载本轮最终 cachebuster，Skill 内容来自实际个人 Marketplace 指向的源码 |
| C-11 | 升级等待活动任务 | 活动快照非空时原升级任务停止且零文件事务；阻塞任务自行归档并释放名额后，用户继续原升级任务完成重扫，不出现后继任务 |
