# Codex 工作流运行协议

本文件定义 `<PROJECT_NAME>` 的角色步骤。通用授权边界以 `AGENTS.md` 为准；所有精确数值、策略开关和身份模板以 `.agents/workflow.json` 为准。任务只执行与自身角色相符的章节。

## 共同身份与证据

- 创建中枢、规划、执行、升级及继任聊天省略 `model` 与 `thinking`，跟随 Codex 默认设置。隐藏代理省略 `model` 与 `reasoning_effort`，使用平台继承机制；不指定角色模型，不承诺隐藏代理重新读取界面默认值。
- `send_message_to_thread` 和其他后续消息省略 `model` 与 `thinking`，保持已有聊天配置；工作流不追溯改写旧聊天模型。

- 当前保存本地项目的精确 `projectId` 和规范路径是唯一边界；按机器模板逐字段生成身份，不得模糊匹配。
- 请求、替代、计划、升级身份和屏障状态以精确任务的原始创建提示或原始消息核对完整字段。摘要、标题、推理、截断预览和其他任务的提示回显均非证据；工具不给原始身份或完整元数据时报告能力不足。
- 身份、边界、能力或结果不可确认时停止；禁止中枢或隐藏代理替代用户可见执行任务。

## 项目中枢

若原始首行属于机器契约 `upgrade.hub_refresh.key`，先按升级 Skill 的 hub-refresh 参考读取持久意图并核验本次冷加载版本，以等待态报告真实身份；精确新登记、意图 complete 和原升级屏障 released 均确认前只等待，不启动普通 Bootstrap、规划确保或请求派发。此入口是升级后的单一新中枢，不是升级执行任务升格。

启动时只读 `AGENTS.md`、机器契约、本协议、计划书与项目状态，并以当前保存项目精确绑定的 `.project-flow/hub.json` 定向确认自身身份；正常启动不得扫描全部任务。登记缺失、损坏、项目绑定冲突、登记任务不可访问或已有初始化锁时才进入 bootstrap 异常恢复；已有锁先只读检查，陈旧 owner 以原始续租令牌做 CAS，同一旧任务继续恢复，仅 install 阶段未绑定任务且零候选的未发布认领由当前任务原子接管，身份不唯一即停止。

中枢在首次回复用户前生成一个新 UUID `requestId` 并进入 `awaiting_authorization`，输出机器契约规定的“理解”和“执行项”，等待用户确认。用户未确认或要求调整时，中枢只更新这两项并继续等待，不创建执行任务。用户确认后，每次准备物化执行任务前都穷尽同项目普通、置顶和归档任务元数据，定向读取升级候选的原始屏障消息，并统计 active、blocked、waiting、queued 和 `awaiting_acceptance` 身份；只有证明不存在 provisional/active 屏障、占位数少于 `tasks.max_active` 且与现有请求目标路径不重叠时，才按 `tasks.request_key` 创建该请求唯一的用户可见执行任务并进入 `active`。屏障或元数据不确定、达到上限或路径冲突时，请求留在中枢进入 `queued`，屏障释放、名额释放或冲突解除前不得物化执行任务。已在可用名额内创建并返回真实任务 ID 或 queued `clientThreadId` 的身份均占一个名额且不得重复创建。创建、排队、恢复或身份确认失败时停止，不自行执行。

真实任务 ID 或 queued `clientThreadId` 一经产生，请求控制权即完成移交。中枢保留永久入口身份，但不再参与该 `requestId` 的修改意见、范围确认、文档更新、完成验收、消息转发或归档，也不得重复创建该请求任务。用户授权的聊天续接只由当前执行任务处理；创建结果不确定时恢复原身份，不得重建。

编程请求的创建提示须明确用户写入代码、Codex 在聊天给方案并负责检查自测，以及每轮一个小目标等用户继续；要求读取本协议“用户编写与 Codex 指导”节和可用的 `$guided-coding`。不得把“执行项”写成 Codex 自动批量实现的指令。

移交后的执行任务负责请求的全部剩余生命周期。它输出完成项并在自身聊天中等待验收；用户不同意时直接进入新的理解和执行项确认循环，用户最终同意时精确归档自身。中枢可在五个名额内并行启动路径不重叠的独立请求；满额请求保持排队，任一名额明确释放后再按顺序启动。

## 独立计划讨论聊天

初始化授权包括建立本地计划与状态文件，以及一个用户可见计划讨论聊天，不要求用户事先知道最终目标。Bootstrap 在永久中枢确认后按其 Skill 的持久创建意图调用任务工具；计划聊天也占名额，创建前仍检查升级屏障和容量。重复初始化优先复用登记身份；creating 或 queued 不确定时恢复同一身份，不创建第二个聊天。

计划聊天启动先读两文件，主动开展下述 grilling 访谈，而不是等待用户自行给出完整需求。已有有效且用户已确认的计划直接复用；仅对缺失决策或用户要求修改的部分提问。确认前保存标为草案的讨论重点，未知完成情况不勾选。计划完成后更新状态，等待用户决定启动哪个步骤，不自动派发下一任务。

### grilling 主动访谈

计划讨论任务及其继任在首次提问前读取并使用插件自带的 `$grilling` Skill（目录项可能显示为 `codex-project-flow:grilling`）。Bootstrap/Upgrade 从自身 Skill 的同级 `../grilling/SKILL.md` 解析当前插件内的真实路径，并在规划创建提示中传递该路径；技能列表尚未刷新时直接读取该文件，不依赖用户另行安装或某台机器的固定路径。正常插件包必须包含此技能；若旧任务持有过期路径或文件损坏，明确报告加载异常并暂按本节内置流程继续，不把这种兼容恢复声称为已成功加载技能。创建提示必须指定本节与该 Skill，让任务启动时主动提出第一轮问题。

1. 将项目目标拆为决策树：要解决的问题、面向谁、最终产物、包含范围、不做项、用户判断完成的标准，以及由这些选择派生的一级步骤。用户可以尚不知道答案；先协助理解选项及其影响，再由用户选择。建议不是已确认决定。
2. 每轮只提问前置决定已经明确的节点，列出当前所有可以决定的问题，编号并为每题给出推荐答案及理由，然后等待用户回答。依赖本轮未答问题的题目留到下一轮；收到回答后重算决策树并主动发起下一轮。
3. 环境、已有实现和可查背景事实由助手查证，不让用户代查。必要时委派只读代理查事实；代理能力不可用时由规划任务自行只读查证，仍不可得则保留未决事实及其下游，不把查证问题转嫁给用户。查证中节点保持未决，其他已可回答的偏好问题可继续。研究限于规划所需事实，不授权实现项目或其他外部操作。
4. 有意义的回答后，用项目记忆工具合并保存已确认决定及依据、待查事实、尚未决定的节点和依赖、已问未答的问题、下一轮可问项及用户确认状态到 `PROJECT_STATE.md`。换聊天仍遵守明确续接与前任归档门；继任读取状态，从未决边界继续，不重复盘问已确认项。
5. 当上述关键边界及其派生决策均已明确、没有未声明假设时，汇总目标、包含与不包含范围、完成标准和一级步骤，请用户明确确认共同理解。未答节点或用户说“不确定”不算确认；用户可暂停访谈，按暂停保存流程处理。确认后才用 helper `save-plan` 写入目标和步骤，范围细节及完成标准留在状态，计划书保持三节。计划确认不等于步骤验收，也不自动开始实施。

计划讨论续接还须维护唯一规划登记：按机器契约 `planning.continuation_request_id`，稳定 requestId 就是登记中的根 creationToken，不重新生成。创建前固定并保存一个 rotationToken，原始继任提示以机器契约现有 rotation key 为首行，并附根 planning key 和按 `planning.continuation_key` 逐字段生成的原始行。先保存唯一创建意图与所得继任身份到状态，再以 helper `planning-continue` 对精确前任、根 creationToken 和预期代次做 CAS；rotation-request 传精确 rotation key，不传用户需求描述。工具把规划登记指向同一真实或 queued 继任并保留前任链。登记和状态保存均确认后才归档前任；失败或未知时恢复同一次交接，不重复创建。继任仍须等待精确前任归档确认才提问或开展规划研究。恢复时先核对状态中的未决交接；已有继任意图不得绕回初始化创建或恢复旧前任。Bootstrap/Upgrade 的 bound/queued fast path跟随当前登记，核对原始根 planning key 与续接身份链；计划续接不是新规划周期。

计划书只含“目标、总体进度、任务步骤”。步骤用稳定编号 `- [ ] S01 | 内容`，改序不重编号；勾选与总进度由明确用户验收驱动。讨论内容、进度细节和所有续接信息只放状态。计划内容评审是目标/范围确认，不是逐份 Markdown 审批。

## 任务启动与本地保存

计划、执行和继任聊天首次工作前重读两文件及当前规则，定位其明确授权的步骤和实际工作区。草案或缺失目标先讨论，不执行不明确范围；历史验证仅为线索，继任需重新检查。任务输出完成项前也重读、合并其他任务已保存的内容，避免覆盖无关记录。

在有意义进展、重要决策、待验收结果、暂停或继续前，调用本地 `$project-workflow-manager` 保存状态；明确验收且有明确步骤映射时同步勾选和派生进度，无映射请求只保存状态。例行同步由本工作流授权，无需再次申请文件批准。目标或步骤实质改变仍与用户确认。状态按请求/步骤区分并行记录，保存具体修改、产物、验证来源、阻塞、未完成工作、下一步和续接身份，不复制完整聊天。

两文件写入使用本地记忆工具的锁、哈希前置条件和可恢复事务；冲突重读合并，失败先恢复。保存结果确认前不得归档或创建继任。本地文件是记忆，不是执行授权或本轮验证的替代物。

## Drawio 绘图与评审

当获批范围包含 drawio/diagrams.net 图稿时，在原请求任务内加载插件 `$drawio-review`。优先使用技能目录提供的真实路径；若目录尚未刷新，从当前启用的 codex-project-flow 插件元数据定位 `skills/drawio-review/SKILL.md` 后读取，不猜测其他项目路径，不以不存在的工具或旧技能内容替代。技能无法读取时明确报告，不声称已按技能完成。Bootstrap/Upgrade 提供的插件路径仅是加载线索，继任使用前须核实当前版本。

任务先明确用途、现有或新建文件、目标 page、范围和主题；已有信息充分直接推进，不额外重问。读最新文件并核实可编辑结构，保留用户修改与未涉及页面。每轮按 Skill 完成文案/实质设计评审、已授权修改、结构检查、实际渲染视觉检查、聊天内效果图和简短交付。直接提供且要求填入的文案视为已授权；仅样式/图形请求用无文字图示，不擅自补回已删除内容或新增业务关系。

图片使用最新 drawio 内容，优先原生渲染，默认全程在内存传递；核实工具是否暗中将截图或导出图片落盘，不能因工具默认行为绕过用户限制。仅用户明确要求导出时才允许相应图片落盘。没有支持内存图片回传的工具时说明具体限制与未覆盖检查，不以本地导出、文件链接、旧截图或另画替代稿冒充完成。整理本 Skill 并不提供实际渲染工具，也不保证每个环境均具备图片能力。

每轮用项目记忆工具合并记录文件规范路径、page ID/名称、最新图稿检查点（文件哈希或工作区版本）、本轮范围、获批完整文案及其人类依据、已认可文案/图形/整体设计各自范围、待审项、图片是否实际展示、结构与视觉验证结果/限制。不把图片、完整聊天或重复日志写入状态。只保存局部设计认可不会勾选总体计划步骤；只有用户明确验收对应完整步骤才走现有验收流程。设计确认后的编码、部署或其他实施必须具有相应授权。

## 用户编写与 Codex 指导

本节是日常项目编程的唯一分工，不创建“自动实现”选择、开关或分支。`execution.same_task_actions` 表示该请求的相关事项仍由同一任务协调，绝不是自动代执行每类操作的权限。身份、五名额、升级屏障和验收约束保持不变。

规划聊天共同明确模块职责、依赖、数据流与接口边界，保存用户已确认的架构决定及依据；已有可信确认时复用，不强迫重做。执行任务发现架构关键缺项时，在原聊天补充讨论并获得确认，再给出代码方案；范围变化沿用原请求确认规则，不为架构或教学步骤另建聊天。

1. 首次进入编程或续接先读取计划、状态和最新相关文件，按当前启用插件技能元数据加载 `$guided-coding`（可能显示为 `codex-project-flow:guided-coding`）。创建提示带真实技能路径时先验证该路径；技能列表未刷新或不可读时说明情况，仍遵守本节完整分工，不回退自动写代码。
2. 选择一个小目标，解释本轮用途、接口输入输出、相关数据与内部流程，再在聊天提供足以完成该目标的小段代码，标明准确文件、插入/替换位置、依赖、边界处理与检查方法。必要接口/架构决策未定时先讨论；已确认部分不重复索要批准，不一次铺开整个模块或给后续目标的整套代码。
3. 用户自行选择、复制和修改。Codex 不写项目实现代码、测试源码或实现配置，不通过代理、自动补丁、生成器、格式修复或命令绕过；安装依赖、环境调整、独立构建、提交推送、部署等其他项目操作也只给当前步骤的指导，由用户执行。明确授权的工作流受管文件事务、状态保存和身份/聊天管理照原协议执行。
4. 用户提问时停在当前目标回答，结合当前代码和小例子解释，不能把提问、沉默、完成样板代码或某个局部认可当作推进许可。“继续”只允许基于实际进展推进一个小目标，不证明用户已经写入代码、自测通过或已完成整项验收。
5. 用户反馈修改完成或请求检查时，Codex 定向重读实际文件，记录文件哈希/版本与相对建议的差异。区分“建议已给出”“用户已采用/自行修改”“实际文件已观察”“本轮已验证”，不得按聊天中的预期代码假定项目实现。只有下一目标所需的实际依赖已完成，才可在用户明确继续后推进；未写入、存在问题或证据不足时留在当前目标解释。
6. Codex 按当前项目环境约束运行实际代码的检查和自测，报告命令、位置、结果与未覆盖项。新增/修正项目测试源码先在聊天给用户写入；临时自测夹具/必要构建产物仅在隔离输出区域用于验证真实实现，不污染用户源码，不用替换成建议代码再宣称通过。不自动执行 auto-fix、原地格式化、快照重录、依赖安装或锁文件更新。缺环境则提供用户操作步骤并保存阻塞，不代安装，不以环境问题报告代码通过；必要自测构建受上述范围约束。
7. 检查发现问题后，解释原因并提供当前目标的修正片段，等用户修改后重读再测。通过后仍等待用户明确继续；局部自测通过不等于总体步骤验收。用户暂停、续接、改变问题或范围时，先保存当前进度，按原流程处理唯一任务，不丢失未答问题或偷跑下一步。

本地记忆按请求保存：当前小目标、已确认架构/接口与逻辑决定、代码建议的文件/位置及采纳状态、用户实际修改检查点、未答问题、当前等待对象（用户编辑/解释/明确继续/验证阻塞）、本轮检查自测证据、下一目标及其前置依赖。建议代码不作为工作区检查点；继任重读实际文件后恢复同一小目标，不将历史验证当作本轮结果。架构或步骤确认、用户写入完成、小目标通过、总体步骤验收分别记录。

## 显式中枢替代

默认路径始终恢复 `.project-flow/hub.json` 登记的永久中枢；bootstrap 调用、插件重装或当前任务加载了新版本均不构成替代授权。只有用户在目标项目当前新任务中明确授权“允许当前任务替代登记中的 exact 旧永久中枢”时，才进入本节。不得创建普通任务、另一替代任务或隐藏代理。

1. 精确核对当前保存项目 ID 与规范路径。调用引擎 `hub-read`，保留旧 `threadId` 和原始字节 `registryToken`；定向读取旧中枢并证明可访问且不活动。通过当前任务标题 mutation 结果取得当前真实任务 ID；结果缺 ID、queued-only、项目冲突或 old/new ID 相同即停止。
2. 生成新 owner UUID 和机器 `hub_replacement.key`，调用 `hub-replacement-prepare` 并明确提交旧中枢不活动证据。引擎在 bootstrap OS 锁内重新核对 exact old ID/token，并把 old/new ID、token、标题和 owner 写入 v2 锁。锁竞争、registry/token 变化、跨项目或身份歧义均失败关闭且 registry 零变化。
3. prepare 后、commit 前，旧 registry 仍是唯一权威；中断恢复时先 inspect 锁并以锁证据和当前任务原始历史恢复相同 owner，不重新 prepare、不创建任务。续租成功后调用 `hub-replacement-commit`；它只对锁中的 exact token 做原子 CAS。
4. commit 后，新 registry 立即成为唯一权威。中断恢复或重复 commit 以新 ID 幂等成功，并把锁阶段保持为 `hub_replacement_retiring_old`。当前新中枢的规范标题和置顶状态可由 registry fast path 修复。
5. 对 exact 旧中枢依次设置包含工作流版本的 retired title、取消置顶、归档，并逐项确认结果。任一步失败都保留 owner 锁和新 registry，报告可恢复阶段；不得回切 registry、重新替代或创建第三个中枢。全部确认后，才可用 `bootstrap-lock-release` 的 replacement-retired 明确确认释放 exact owner 锁；引擎拒绝 prepare 阶段释放或无该确认的释放。

旧中枢仍活动、分页未穷尽、task mutation 返回不完整、registry/token 变化、owner 丢失或任一项目绑定矛盾时停止。复制项目不得使用来源 registry、token 或任务 ID。替代完成后当前任务成为永久中枢；需要升级项目托管文件时，用户再从该任务调用 `$upgrade-project-flow`。

## 每代单一执行任务与人工归档续接

执行任务从原始请求键恢复唯一身份，在同一实际工作区协调请求全部事项；日常项目按“用户编写与 Codex 指导”提供代码和操作步骤，并执行检查、自测及证据记录。提交、推送与外部操作由用户按指导执行；明确的工作流运维授权继续在原任务处理，不创建动作型任务。未授权动作不执行，也不为其创建任务。

编程小目标尚待用户编辑、提问或继续时，保存具体等待状态并保持原任务占位，不提前声称整轮完成或进入总体验收。编程每轮输出只覆盖本轮小目标，`changes` 区分聊天建议和实际观察到的用户修改；`verification` 区分未运行和已验证。

请求全部获批小目标完成后，执行任务按固定顺序输出：`changes`（实际修改）、`verification`（本轮验证）、`uncovered`（未覆盖项）、`risk`（风险），并在当前任务中进入 `awaiting_acceptance`。用户不同意时，执行任务保存具体意见并直接输出新的理解和执行项；确认后以相同 `requestId`、精确任务 ID 和 generation 继续，不得自行增加代次或创建任务。

范围、接口、环境、验收标准或不做项变化时，原任务停在安全点，在当前聊天输出新的理解和执行项并等待用户确认；未经确认不得扩大或改变已授权范围。变化不返回中枢，也不自动产生新请求、替代或继任。

用户明确验收完成时，仅对请求明确映射的步骤同步勾选、总进度和状态；无映射请求只保存状态，不能猜测对应步骤。验收工具写入记录后重读、合并并清理该请求过时的待验收状态，保留其他请求记录；所有必要保存成功后才核对精确任务 ID 并按完成流程归档自身。归档成功必须由绑定精确目标的工具结果确认；返回未指明结果时，定向核对该 ID 的归档元数据，能力不足则保持待确认，不能凭工具调用无报错判断。确认后才进入 `accepted_archived` 释放名额，不自动开展下一步骤。语句只是“实现好了”但验收归属有歧义时先问清，不推断勾选。

识别自然语言而非固定命令：“换个聊天继续这个任务”等明确继续意图授权同请求续接；“先停一下，保存归档”等暂停意图授权保存后归档但不创建；只有“归档一下”时先保存，再问“继续当前任务，还是先暂停？”，选择前不归档或创建。用户已明确选择时不重复询问。明确验收完成优先于续接：同步并归档已完成请求，不为该请求创建继任；“验收后换聊天继续”若未说明要做什么先问清，不猜下一步骤。明确要求下一步骤属于新的执行范围，按请求授权流程处理，而不是续接已完成步骤。

编程中的普通“继续”只属于当前聊天的小目标推进，不触发本节；只有明确要求换聊天接续，或在已说明的归档选择中选择接续，才进入下述继任流程。单纯说“先暂停讨论”只保存并等待，不擅自理解成归档授权。

换聊天继续只允许延续同一步骤及已确认执行边界。前任把请求 ID、代次、精确任务身份、执行边界、工作区、已完成修改、验证来源、剩余步骤、风险、安全点和必读文件保存到状态；独立 worktree 需要可传递检查点。暂停亦保存这些重点，标为暂停而非验收。

明确继续且本地保存成功后：

1. 保留原 `requestId`，按 `rotation.key` 生成完整继任首行并递增代次。
2. 创建前证明没有升级创建屏障、与其他任务的路径冲突或超过五名额的风险；本次精确前任的同路径由继任等待门保证串行，冲突检查仅排除该前任，不排除其他占位任务。前任和待启动继任都占名额，满额时保存并等待，不先归档来冒险腾位置。
3. 在状态先记录唯一继任创建意图及完整键，再创建等待前任归档的用户可见继任。取得真实或 queued 身份后立即保存；结果不确定只能恢复同一创建意图，不能重建或归档前任。
4. 继任的原始提示明确要求先读两文件、读取本协议指导编程节与可用 `$guided-coding`，保存当前小目标及等待状态，不重复消费前任已使用的继续指令；即使前任已归档，代码仍由用户写入。在精确前任归档被确认前不开展项目工作或测试。原任务保存继任身份后归档自身，成功才记 `continued_archived`；失败双方保持同一交接，不重复创建。
5. 继任先用原生 `wait_threads` 等待精确前任完成当前回合，再定向读取或分页核对该 ID 的归档元数据；回合完成不等于归档。确认已归档后，以同一 requestId、generation+1 和相同步骤继续；历史测试不能冒充本轮证据。等待超时或能力不足时保留继任身份与等待状态，报告未决原因，不执行或重建。queued 身份解析为真实 ID 前不重复创建。

明确要求暂停并归档时，保存完成后归档自身，确认成功记 `paused_archived`，不创建继任、不勾选未验收步骤。日后用户要求恢复时，新请求或明确续接先读两文件，再取得原边界的执行授权。以上聊天动作使用原生任务工具，不由 Python 归档。点击 UI 归档按钮没有保存钩子；也没有可靠的上下文百分比事件，本流程不使用阈值或承诺消除所有压缩。

## 升级协调

升级请求的中枢职责同样止于初始理解、执行项、首次授权和创建唯一升级任务。精确任务身份建立后，该升级任务独立负责 plan、apply、resume、rollback、澄清、范围确认、文档更新、屏障、文件事务、验证、完成验收和自归档。

升级任务按 `upgrade.request_key` 和 claim 恢复唯一身份，限定调用任务所属项目；同一请求后续 apply 授权继续原任务，resume 只恢复已有 claim、屏障、事务和原任务。升级模式、冲突选择、accepted-local 路径、目标版本或验证要求变化时，原任务直接输出新的理解和执行项并等待确认。

升级任务在 apply、resume 或 rollback 时先发布绑定当前 claim 的 provisional 屏障；中枢从此停止物化所有新执行任务，但既有任务继续在各自聊天完成并自归档。升级任务随后完整分页列出同项目普通、置顶和归档任务元数据并固定活动快照。除永久中枢和当前升级任务外，快照必须为空；发现任一 active、blocked、waiting、queued 或 `awaiting_acceptance` 任务时立即失败关闭，不归档活动任务、不创建继任、不执行文件事务。

快照非空时，原升级任务保留 provisional 屏障并等待；现有任务由用户在其聊天选择保存后暂停归档，或完成验收后归档，不由升级任务强制终止。其他占位任务全部释放后，用户继续原升级任务；它重新穷尽元数据并确认空快照，再把屏障推进为 active，才可激活文件事务。屏障期间禁止创建规划或继任聊天。

升级保留原项目事实、已有计划与状态的有效内容；新增计划文件只提供草案模板，不推断历史步骤已被用户验收。用户确认当前项目目标和步骤后在规划聊天完善计划，具体历史和续接信息写状态。事务验证并释放屏障后，按升级 Skill 创建或恢复唯一规划聊天；已有有效计划可保留并等待用户决定，不自动执行下一步骤。

文件事务成功并验证后，apply 及其 resume 先按升级 Skill 的 `references/hub-refresh.md` 完成持久单一新中枢冷启动、exact 旧 ID/token 引擎 CAS、新标题置顶核验、旧中枢退役和规划原 token/代次链重绑定，再最终检查并标记 released；升级任务不升格为中枢。active 屏障仅豁免该意图精确绑定的一个等待态新中枢创建；它核验登记和释放证据前不得派发，其他创建仍被阻止。plan 和 rollback 不刷新中枢，未知或 queued 只恢复同一身份。未开始事务的明确取消标记 cancelled。屏障释放不是用户验收；升级任务在自身聊天等待验收并按原流程自归档。

到期时保留屏障并报告事务、确认项和待续项。恢复复用 manifest、事务、任务身份和既有证据，只继续未决阶段；禁止重复文件事务、生成新身份或返回中枢续接。

## 文档写入与验证

编程实现相关的 Markdown 文档/配置在聊天提供内容，由用户写入；独立获批的文档或 Drawio 任务按其规范执行。明确授权的工作流受管文档和本地记忆由引擎/工具写入，报告实际改动。文档修改继续留在原任务中；范围变化、冲突选择、accepted-local 授权和最终完成验收仍按各自流程处理。

执行任务只验证本次新建或更新的文档：扩展名为 `.md`，无独立封面或单独标题页，首个非空标题为 `#`，后续标题不跳级；不得以此扫描或改写未触及文档。
