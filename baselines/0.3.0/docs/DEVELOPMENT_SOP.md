# 开发与验证标准作业流程

## 1. 适用范围

本 SOP 适用于文件修改、检查、构建、测试、文档同步、提交、推送和外部操作。纯问答、解释和只读查询属于 Work。

当前会话中由用户确认的目标、范围、不做项、目标环境、验收标准和授权项目是执行基线。`docs/PROJECT_STATE.md` 只提供长期状态，不提供需求或授权。

## 2. 最小流程

1. **Work**：只读了解实现和文档，确认目标、范围、不做项、环境、验收标准与待确认事实。
2. **授权**：将修改、检查、构建、测试、文档同步、提交、推送和执行任务轮换分别列为细小编号项。
3. **执行**：只完成用户选择的编号项，保持改动聚焦。
4. **验证**：按已确认标准执行，记录位置、操作、实际结果和未覆盖项。
5. **收尾**：报告实际结果；只有长期状态确实变化且文档同步已获授权时才更新项目状态。

## 3. 授权边界

- 为形成执行项所需的只读检查无需额外授权。
- 各工作项互不自动绑定；只执行用户明确选择的编号项。
- 文档同步、提交和推送始终需要各自授权。
- 执行任务轮换是独立授权项，只延续当前已授权的目标、范围、不做项、环境、验收标准和动作，不授予新动作或扩大权限。
- 新增工作项，或需求、范围、接口、协议、环境、验收标准发生变化时，立即停止并回到 Work。
- 一次性要求不自动成为长期规则；长期机制变更必须明确授权。

## 4. 活动任务与执行顺序

- 项目中枢是永久协调入口，不占后续活动执行任务名额，也不因开始新工作而重复创建。
- 默认最多保留一个由中枢协调的用户可见后续活动执行任务。
- 阻塞或等待中的后续活动执行任务仍占用这个名额。
- 高风险操作和外部操作串行执行。
- 当前产品具备任务管理能力时使用该能力维护后续活动执行任务；不具备时在当前中枢任务继续并如实说明。
- 优先在里程碑或一次完整的“修改—验证”周期结束时轮换。第 6 个实质执行轮次开始评估，第 10 个实质执行轮次前在最近安全点完成轮换；上下文压力或用户请求也触发轮换。
- 需求、范围、接口、协议、环境或验收标准变化时先回到 Work；不得以轮换替代重新确认。
- 轮换前按 `.agents/prompts/09_execution_handoff.md` 形成交接包，由项目中枢确认完整。确认后先归档前任，再创建继任；继任重新读取项目规则并核对实际工作区后才继续。
- 创建前生成版本化 `rotationKey` 并作为继任首条用户消息第一行。创建继任失败且没有任务 ID 时，恢复前任；仅返回 `clientThreadId` 时视为排队中并占用唯一任务槽，保留完整键且不得重复创建。物化后穷尽同项目任务，只按首条用户消息第一行的完整键精确恢复唯一继任。
- 独立 Git worktree 中的执行任务，只有在代码状态已形成授权范围内、可供继任读取的可传递检查点时才轮换。
- 只有需要协调后续、要求用户选择或用户明确要求时才回传。

## 5. 实施原则

- 只实现已确认范围，优先复用现有实现、工具和验证入口。
- 不顺带增加功能、重构无关内容、整理目录或修复范围外问题。
- 保留并绕开工作区中的无关改动，不覆盖、不回滚、不擅自纳入提交。
- 需要修改未授权文件、扩大验证范围或改变目标环境时立即暂停。
- 新增测试脚本或辅助工具必须单独说明必要性并获得授权。

## 6. 证据与验证

- **文档或代码确认**：只能说明静态存在与当前理解。
- **静态检查**：记录实际执行位置、命令和结果。
- **构建或测试**：记录实际环境、命令、结果和未覆盖项。
- **用户或外部环境回传**：标明来源，不与本地结果混写。
- 未实际运行的检查、构建或测试不得写成通过。
- 历史记录、计划、他人结论和代码存在不能替代本轮证据。
- 轮换交接中的历史验证只能作为背景；继任任务不得把它表述为本轮验证结果。
- 缺少环境、权限或外部依赖时，停止相关步骤并记录缺失条件。

## 7. 状态与收尾

- `docs/PROJECT_STATE.md` 只记录当前目标、当前进展、重要结论和下一步。
- 执行任务交接包属于临时协调信息，不写入 `docs/PROJECT_STATE.md`。
- 只有这些长期状态实质变化，且文档同步已获授权时，才使用 `$project-workflow-manager` 更新。
- 报告实际修改、证据、未运行项、未覆盖项和潜在风险。
- 没有协调、选择或明确回传要求时，直接在当前任务中收尾。
