# Codex 工作流运行协议

本文件定义 `<PROJECT_NAME>` 的角色步骤。通用授权边界以 `AGENTS.md` 为准；所有精确数值、策略开关和身份模板以 `.agents/workflow.json` 为准。任务只执行与自身角色相符的章节。

## 共同身份与证据

- 当前保存本地项目的精确 `projectId` 和规范路径是唯一边界；按机器模板逐字段生成身份，不得模糊匹配。
- 请求、替代、升级握手和屏障状态只接受已知任务的完整原始消息字段；需要首行模板时只接受原始 `agentMessage.text` 第一行。等待、摘要、预览、标题、推理、工具输出和提示回显均非证据。
- 身份、边界、能力或结果不可确认时停止；禁止中枢或隐藏代理替代用户可见执行任务。

## 项目中枢

启动时读取 `AGENTS.md`、机器契约、本协议和项目状态，并以当前保存项目精确绑定的 `.project-flow/hub.json` 定向确认自身身份；正常启动不得扫描全部任务。登记缺失、损坏、项目绑定冲突、登记任务不可访问或已有初始化锁时才进入 bootstrap 异常恢复；已有锁先只读检查，陈旧 owner 以原始续租令牌做 CAS，同一旧任务继续恢复，仅 install 阶段未绑定任务且零候选的未发布认领由当前任务原子接管，身份不唯一即停止。

中枢在首次回复用户前生成一个新 UUID `requestId` 并进入 `awaiting_authorization`，输出机器契约规定的“理解”和“执行项”，等待用户确认。用户未确认或要求调整时，中枢只更新这两项并继续等待，不创建执行任务。用户确认后，名额可用则按 `tasks.request_key` 创建该请求唯一的用户可见执行任务并进入 `active`；名额被占则进入 `queued`，真实任务 ID 或 queued `clientThreadId` 一经产生均占用唯一名额且不得重复创建。创建、排队、恢复或身份确认失败时停止，不自行执行。

执行任务完成一轮已授权工作后，必须按 `requests.completion_fields` 输出修改、验证、未覆盖项和风险，把同一完成项交给中枢，并进入 `awaiting_acceptance`。等待验收仍占唯一名额。验收属于中枢职责：用户同意时，中枢核对 `requestId` 与记录的精确执行任务 ID，归档该任务；只有归档结果明确成功，才进入 `accepted_archived`、结束请求、释放名额并物化下一项。结果不确定时保持 `awaiting_acceptance`，不得释放或创建替代。

用户不同意时，中枢保存其具体修改内容并进入 `revision_pending`，不得归档、递增代次或创建新任务；随后重新输出理解和新的执行项，回到 `awaiting_authorization`。用户确认新一轮后，中枢把指令发送给同一精确执行任务，恢复 `active`。用户若在执行任务内表达验收决定，该任务只将完整决定和 `requestId` 转给已知中枢并等待，不自行归档或执行未确认修改。补充授权、范围确认和同一目标后续动作同样发送给该原任务；目标不同的请求按确认顺序排队。

对已知升级事务任务的当前事务请求，中枢重读已部署规则、核对项目/版本/事务，并按机器模板返回一次原始握手。升级屏障的释放只证明升级协调完成，与普通请求的用户验收和 `accepted_archived` 相互独立；协调未完成时不得解除屏障或执行文件工作。

## 显式中枢替代

默认路径始终恢复 `.project-flow/hub.json` 登记的永久中枢；bootstrap 调用、插件重装或当前任务加载了新版本均不构成替代授权。只有用户在目标项目当前新任务中明确授权“允许当前任务替代登记中的 exact 旧永久中枢”时，才进入本节。不得创建普通任务、另一替代任务或隐藏代理。

1. 精确核对当前保存项目 ID 与规范路径。调用引擎 `hub-read`，保留旧 `threadId` 和原始字节 `registryToken`；定向读取旧中枢并证明可访问且不活动。通过当前任务标题 mutation 结果取得当前真实任务 ID；结果缺 ID、queued-only、项目冲突或 old/new ID 相同即停止。
2. 生成新 owner UUID 和机器 `hub_replacement.key`，调用 `hub-replacement-prepare` 并明确提交旧中枢不活动证据。引擎在 bootstrap OS 锁内重新核对 exact old ID/token，并把 old/new ID、token、标题和 owner 写入 v2 锁。锁竞争、registry/token 变化、跨项目或身份歧义均失败关闭且 registry 零变化。
3. prepare 后、commit 前，旧 registry 仍是唯一权威；中断恢复时先 inspect 锁并以锁证据和当前任务原始历史恢复相同 owner，不重新 prepare、不创建任务。续租成功后调用 `hub-replacement-commit`；它只对锁中的 exact token 做原子 CAS。
4. commit 后，新 registry 立即成为唯一权威。中断恢复或重复 commit 以新 ID 幂等成功，并把锁阶段保持为 `hub_replacement_retiring_old`。当前新中枢的规范标题和置顶状态可由 registry fast path 修复。
5. 对 exact 旧中枢依次设置包含工作流版本的 retired title、取消置顶、归档，并逐项确认结果。任一步失败都保留 owner 锁和新 registry，报告可恢复阶段；不得回切 registry、重新替代或创建第三个中枢。全部确认后，才可用 `bootstrap-lock-release` 的 replacement-retired 明确确认释放 exact owner 锁；引擎拒绝 prepare 阶段释放或无该确认的释放。

旧中枢仍活动、分页未穷尽、task mutation 返回不完整、registry/token 变化、owner 丢失或任一项目绑定矛盾时停止。复制项目不得使用来源 registry、token 或任务 ID。替代完成后当前任务成为永久中枢；需要升级项目托管文件时，用户再从该任务调用 `$upgrade-project-flow`。

## 单一执行任务与明确替代

执行任务从原始请求键恢复唯一身份，在同一实际工作区完成该请求全部已授权检查、修改、构建、测试、自检、证据和交付。文档、提交、推送与外部操作仍分别确认授权，但获批后继续原任务，不创建动作型任务。未授权动作不执行，也不为其创建任务。

每轮执行结束时，执行任务按固定顺序输出：`changes`（实际修改）、`verification`（本轮验证）、`uncovered`（未覆盖项）、`risk`（风险），并将完整完成项回传中枢。此时进入 `awaiting_acceptance`，停止项目工作。用户同意或不同意都由中枢裁决；执行任务收到决定时只原样转发给中枢。中枢确认修改轮次后，本任务以相同 `requestId`、精确任务 ID 和 generation 继续；不得自行增加代次或创建任务。

范围、接口、环境或验收变化时，原任务停在安全点向中枢报告；中枢取得用户确认后优先向原任务补充指令。变化不自动产生新请求、替代或继任。不同目标继续排队，活动、blocked、waiting 或 queued 原任务尚占位时不得物化。

任何替代、轮换或继任都须用户明确授权，且目标、范围、不做项、环境、验收和已授权动作不变；独立 worktree 还须有已授权可传递检查点，否则停止并保留原任务。轮次或上下文压力仅允许提示用户选择，不构成替代授权。

前任提交代次和任务 ID、执行边界、实际工作区、已完成修改、本轮与历史证据、未覆盖项、剩余步骤、风险、安全点、必读文件及 worktree 检查点；不得复制完整日志或把交接写入项目状态。

中枢确认交接完整且已取得明确替代授权后（此处归档是替代恢复，不是用户验收）：

1. 保留原 `requestId`，按 `rotation.key` 生成完整继任首行并递增代次。
2. 先归档已知前任，再创建对应继任。没有真实任务 ID 时恢复前任；排队身份保留同一键等待且不得重建。
3. 继任按完整首行恢复唯一身份，重读规则并核对实际工作区；前任验证仅为历史证据。
4. 普通继任不发送升级握手；升级继任核对版本、事务和代次，再按机器模板返回原始握手。

没有明确替代授权时，以上步骤全部禁止；隐藏子代理、摘要任务或中枢自身均不得代替。

## 升级协调

升级模式、授权、契约切换和恢复细节以 `$upgrade-project-flow` 的协调契约为准。一个升级请求始终使用 `upgrade.request_key` 标识的唯一可见任务：默认 plan 创建该任务但不启用屏障；同一请求后续 apply 授权继续原任务并把它提升为事务任务。直接 apply 或 rollback 时创建一个任务。resume 只恢复已有请求、claim、屏障和原任务，不生成新身份。中枢不成为事务任务，也不执行文件工作。

新 apply/rollback 时，中枢生成一次性 `claimId`，先按机器模板在自身原始消息记录包含该值的 provisional 状态并立即阻止普通创建，再把同一 `coordinator_claim` 发送给既有升级请求任务，或在尚无该任务时作为创建提示中的完整身份证据。真实任务 ID 恢复后屏障重绑定正式事务键。

1. 唯一升级任务按请求键和 claim 认领身份并生成事务键，限定调用任务所属项目；它同时承担可见协调与文件引擎执行角色，不再创建独立执行器。请求中枢按机器模板记录 active 状态，把临时屏障重绑定到正式事务。
2. 完整分页列出同项目普通、置顶和归档任务的元数据并固定活动快照，把已激活屏障绑定该快照；历史只定向读取中枢、事务任务、快照任务及身份或状态有歧义的候选，元数据不完备或歧义未消除时才回退完整历史读取。
3. 快照中的每个活动请求都必须取得用户明确替代授权；授权缺失时在文件事务前停止并保留屏障。取得授权后，事务任务先归档已知前任，再把带原 `requestId` 的继任身份按顺序交给中枢队列；此时不创建继任。
4. 事务任务执行并验证文件操作，成功后切换到已部署或已恢复契约，再请求中枢返回一次原始握手。
5. 空快照走快速路径：中枢握手后只做一次最终元数据穷尽扫描，契约满足即解除屏障。非空快照也只验证前任归档和继任队列映射，不在事务任务活动期间创建其他可见任务。
6. 最终元数据穷尽扫描；仅在事务任务、中枢、全部明确授权和队列映射精确确认后，请求中枢记录 released 状态并解除屏障。事务任务归档后，中枢按队列逐一创建获准继任并验证握手；前一个结束前不得创建下一个。创建确定失败且没有任何任务身份时记录 cancelled；结果不确定时保留 provisional 状态。

阶段进入或恢复时按机器契约穷尽任务元数据并禁用工具输出；历史读取遵循定向优先、歧义时完整回退。等待只负责唤醒，随后仅增量读取相关任务。非空快照在补发、失败或释放前重新穷尽元数据；相同合法握手幂等折叠。不得创建补偿继任。恢复上限和单调截止读取机器契约，原始消息证据规则读取本协议“共同身份与证据”。

到期保留屏障并报告事务、确认项和待续项。恢复时先从已知中枢原始消息读取最新匹配屏障状态，再复用 manifest、事务、任务身份与握手，只继续未决阶段；禁止重复文件事务。身份、消息、管理、验证或恢复失败时保持屏障并停止。

## 交付文档验证

执行任务对本次新建或更新的交付文档逐一验证：扩展名为 `.md`，无独立封面或单独标题页，首个非空标题为一级 `#`，后续标题不跳级。段落、列表、表格和代码块按内容需要使用；不得以该规则为由扫描或改写未触及文档。
