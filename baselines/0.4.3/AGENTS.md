# Codex 项目协作规则

适用范围：本文件位于仓库根目录，适用于整个 `<PROJECT_NAME>` 项目。子目录中的 `AGENTS.md` 可以增加更具体的规则。

## 项目事实

- 在这里记录少量、稳定、会影响实施判断的项目事实。
- 当前任务、临时阻塞、短期进度和未经确认的推测不属于项目事实。
- 未填写的事实保持未知；不要根据模板示例或常见目录结构自行补全。

## 按需读取

- `AGENTS.md` 的“项目事实”二级章节和 `docs/PROJECT_STATE.md` 属于项目内容；工作流升级必须保留它们。其他由 `managed-files.json` 标记为插件所有的内容按新版插件更新。
- 需要规则、执行流程或长期状态时，按 `.agents/workflow.json` 读取对应路径。
- 修改文件、检查、构建、测试、文档同步、提交、推送或外部操作前，先读取开发 SOP。
- 处理具体模块时，优先读取该模块最近的 `AGENTS.md`、README、接口说明和已有验证入口。
- README 不足时先搜索文件名、标题和关键词，只读取命中段落。
- 首轮最多完整读取一份 README，并追加两个相关文档片段；补充内容累计不超过 8,000 字符。
- 单个文档超过 6,000 字符时，先读取标题和命中范围，不直接全文加载。
- 仍缺少必要信息时，说明缺口并围绕具体问题继续扩展；只有用户明确要求全面审计时才遍历文档目录。

## Work 与授权

- Work 只用于只读分析、澄清和设计，不修改文件，不执行检查、构建、测试、文档同步、提交、推送或外部操作。
- 变更前确认目标、范围、不做项、目标环境和验收标准。
- 项目中枢只允许分析、澄清、设计、编号、创建、等待和协调用户可见活动执行任务，以及汇总这些任务的结果；不得在中枢内修改文件、执行检查、构建、测试、文档同步、提交、推送或外部操作。
- 将文件修改、检查、构建、测试、文档同步、提交、推送和执行任务轮换分别列为细小的编号项；每个执行编号项都必须明确要求创建对应的用户可见活动执行任务。
- 用户选择执行编号只代表授权创建对应的用户可见活动执行任务，不代表授权项目中枢回退执行该项。
- 项目中枢是永久协调入口，不占后续活动执行任务名额；中枢之外默认最多保留五个由中枢协调的用户可见活动执行任务。
- 阻塞、等待或排队中的用户可见活动执行任务仍各占用一个名额。
- 任务管理能力不可用、任务创建失败、创建结果无法继续管理或无法确认任务身份时，项目中枢必须停止并报告；禁止回退到中枢执行，隐藏子代理也不得替代用户可见活动执行任务。
- 工作流升级使用一个临时、用户可见、只负责协调的升级协调器；它占用活动任务名额，只能按 `.agents/prompts/10_upgrade_coordination.md` 发现任务、激活或保持升级屏障、创建升级执行任务、等待、消息协调、归档旧任务、创建预期继任并核对版本握手。它不得修改文件、运行检查或测试、提交、推送或扩大原任务授权。
- 用户明确要求应用工作流升级时，同时授权升级协调器创建一个用户可见升级执行任务，以及为同一事务中已快照活动任务创建必要的继任；文件冲突处理、范围变化、提交、推送和其他动作仍需各自授权。
- 升级屏障激活后禁止创建普通执行任务。只有精确升级执行任务和与快照前任一一对应的继任可以创建；中枢握手和全部任务版本握手完成前不得解除屏障。
- 执行任务轮换是独立授权项，只允许在同一目标、范围、不做项、环境、验收标准和已授权动作内延续执行；不得借轮换扩大权限。
- 新增工作项，或需求、范围、接口、协议、目标环境、验收标准发生变化时，立即停止执行并回到 Work 重新确认。
- 一次性要求不会自动成为长期规则；修改 `AGENTS.md`、SOP、Prompt、Skill 或其他长期机制必须获得明确授权。

## 修改与执行

- 改动保持小而聚焦，不顺手增加功能、重组目录或修复范围外问题。
- 工作区可能已有用户改动；保留并绕开无关变更，不覆盖、不回滚、不擅自纳入提交。
- 优先复用现有实现、工具和验证入口；新增测试脚本或辅助工具必须作为独立工作项说明并授权。
- 无冲突的用户可见活动执行任务可以并行；高风险操作和外部操作必须串行执行。需要新增权限、外部协调或不可逆选择时先请求确认。
- 文档同步、提交和推送都是独立工作项，不因源码修改而自动获得授权。

## 执行任务轮换

- 以完成一个里程碑或一次完整的“修改—验证”周期作为首选轮换点；单个执行任务在第 6 个实质执行轮次开始评估，并最迟在第 10 个实质执行轮次的最近安全点轮换。
- 出现上下文压力或用户请求时也触发轮换；若同时发生新增工作项，或需求、范围、接口、协议、环境、验收标准变化，先回到 Work，不得直接轮换继续执行。
- 轮换前按 `.agents/prompts/09_execution_handoff.md` 形成交接包。项目中枢确认交接完整后，先归档前任，再创建继任；继任必须重新读取规则并核对实际工作区。
- 创建继任前生成版本化 `rotationKey`，并将它作为继任首条用户消息的第一行。创建失败且没有返回任务 ID 时，恢复前任继续占用原任务槽；只返回 `clientThreadId` 表示仍在排队并已占用任务槽，不得重复创建。物化后只按同项目首条用户消息中的完整键精确恢复唯一继任。
- 交接包不写入 `docs/PROJECT_STATE.md`。历史检查、构建或测试结果必须标为历史信息，不能冒充继任任务的本轮证据。
- 使用独立 Git worktree 时，只有代码状态已经形成授权范围内、可供继任读取的可传递检查点，才允许轮换。

## 工作流升级协调

- `$upgrade-project-flow` 只能升级调用它的当前任务所属项目。计划和应用都必须先核对当前任务的精确项目 ID 与规范化工作目录；用户指定其他项目时，在读取对方清单、管理对方任务或修改对方文件前停止，并要求在目标项目的新任务中重新调用，禁止跨项目升级或协调。
- 升级协调器先穷尽发现同项目任务，确认唯一永久中枢和活动任务快照，再激活任务创建屏障并创建独立的用户可见升级执行任务。发现、创建、等待、消息或身份确认失败时保持失败关闭，不得回退执行。
- 文件升级成功后，把脚本返回的精确事务 ID 绑定到本次协调。升级协调器让永久中枢重新读取新版规则并完成中枢握手，然后让仍需继续的旧版活动任务在安全点交接、归档并自动创建新版继任。
- 插件所有的工作流内容出现 B/L/N 双向修改时自动采用新版；`AGENTS.md` 的“项目事实”章节通过受保护合并保留，`docs/PROJECT_STATE.md` 始终保留。没有旧基线的新增路径若已被不同文件占用，仍停止并报告。
- 中枢与继任握手只接受精确已知任务中原始 `agentMessage` 文本的完整第一行；等待结果只用于唤醒，标题、摘要、预览、`latestAssistantMessage`、状态说明、推理摘要、工具输出、截断或转换文本和用户提示回显都不是握手或空响应证据。每次等待后、补发前和失败前必须完整分页读取该任务的全部历史。
- 刚完成轮次的空读取只是暂时不可见。只有同一终止轮次连续三次完整历史快照均无新增原始消息，且快照之间经过有界等待，才算稳定空响应。发现有效握手立即接受；同一精确任务、事务、版本和代次的完全相同握手重复出现时幂等折叠，不算歧义。
- 升级继任首条用户消息使用 `[codex-project-flow:execution:v2]` 完整键，并包含精确项目 ID、中枢任务 ID、前任任务 ID、正整数代次、目标工作流版本和文件升级事务 ID。继任读取规则和工作区后返回 `[codex-project-flow:handshake:v1]` 完整版本握手。继任连续两次稳定空响应时，只允许归档该空响应任务并创建一个代次加一、以前者为前任的补偿继任；补偿继任不得再次替换。中枢稳定空响应只允许一次同任务补发，不创建替代中枢。
- 活动任务快照为空时，文件事务和中枢原始握手成功后直接解除屏障，不创建继任。其他情况下，只有中枢握手成功，且快照任务逐项完成、明确无需继任或由唯一握手成功的继任替换后，才解除屏障。升级期间的新普通工作等待解除后回到 Work 重新编号。

## 证据与报告

- 区分四类证据：从代码或文档确认、静态检查、实际构建或测试、用户或外部环境回传。
- 未实际执行的检查、构建或测试不得写成通过；历史结果和代码存在不能替代本轮证据。
- 报告实际执行位置、操作、结果、未运行项和未覆盖项。
- 依赖缺失环境、权限或外部服务时，明确写出缺失条件和待验证内容。
- 只有长期目标、当前进展、重要结论或下一步发生实质变化，且文档同步已获授权时，才使用 `$project-workflow-manager` 更新项目状态。
- 只有需要协调后续、要求用户选择或用户明确要求时，才按 `.agents/prompts/08_result_handoff.md` 回传。

## 项目状态

- `docs/PROJECT_STATE.md` 是唯一动态项目状态。
- 它只记录当前目标、当前进展、重要结论和下一步，不提供任务需求、执行授权或本轮验证证据。
- 稳定知识应写入对应架构、模块或接口文档，不把项目状态扩展成日志、风险库或决策档案。
