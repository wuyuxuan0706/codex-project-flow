# Codex 项目协作规则

适用于整个 `<PROJECT_NAME>` 项目；更深目录的 `AGENTS.md` 可增加局部规则。

## 项目事实

- 只记录少量、稳定且影响实施判断的事实；未知内容不得猜测。

## Work、请求与执行

- “项目事实”节和 `docs/PROJECT_STATE.md` 属于项目内容，升级时保留；其他托管内容采用新版。
- Work 只负责新请求的初始分析、澄清和设计。中枢在首次回复前生成 `requestId`，输出“理解”和“执行项”并等待用户确认；未经确认不得创建执行任务或执行项目工作。
- 每个获批请求只创建一个用户可见执行任务。真实任务 ID 或 queued `clientThreadId` 建立后，该请求的全部后续沟通和工作都移交给执行任务；补充授权、范围确认和修改轮次继续同一精确任务和代次。
- 角色步骤读取 `.agents/WORKFLOW_PROTOCOL.md`；名额、排队、替代、恢复上限和身份模板读取 `.agents/workflow.json`。
- 按模块读取最近规则和实际入口。活动任务保留无关改动，只在实际环境执行已授权范围。
- 报告执行位置、操作、本轮证据和未覆盖项；计划、代码存在和历史结果不能替代本轮验证。

## 中枢与授权

- 中枢只负责接收新请求、生成 `requestId`、输出初始理解和执行项、等待首次授权，以及创建该请求唯一的用户可见执行任务；不得修改或检查文件、构建、测试、同步文档、提交、推送或执行外部操作。
- 执行任务取得真实任务 ID 或 queued `clientThreadId` 后，该请求的控制权即移交给执行任务。中枢不得继续处理该请求的修改意见、范围确认、文档评审、完成验收、消息转发或归档。
- 中枢不得为同一 `requestId` 创建第二个执行任务。创建结果不确定时停止并恢复原身份，不得重建。
- 中枢永久存在且不占执行名额；中枢之外最多五个用户可见执行任务。active、blocked、waiting、queued 或 `awaiting_acceptance` 身份都占名额；满五后新请求留在中枢排队，名额释放前不得物化其执行任务。
- 目标独立且路径不重叠的请求可在空余名额内并行。每个请求仍只绑定一个精确执行任务；同一请求、目标路径重叠的请求和升级文件事务保持串行。
- 执行任务负责移交后的全部沟通和工作，包括检查、修改、构建、测试、文档评审、补充授权、范围确认、完成验收和恢复。
- 用户提出修改或改变范围时，执行任务不得直接扩大原授权；它必须在当前任务中输出新的理解和执行项并等待用户确认。确认后以相同 `requestId`、任务 ID 和 generation 继续。
- 执行任务完成一轮工作后固定输出修改、验证、未覆盖项和风险，并在当前任务中等待用户验收。用户不同意时，原任务直接进入新的理解和执行项确认循环，不返回中枢。
- 用户最终同意后，执行任务归档自身。只有归档结果明确成功且指向当前精确任务，才标记 `accepted_archived`、结束请求并释放名额；归档失败或结果不确定时保持打开并报告。
- 中枢身份以当前保存项目绑定的 `.project-flow/hub.json` 为快速入口；正常启动只定向核对登记任务，登记缺失、损坏、冲突或锁恢复时才全量发现。已有初始化锁先按机器契约只读检查；陈旧锁按 owner CAS 恢复同一任务，尚未发布且无任务 ID 的孤儿认领可由当前任务接管，其他锁竞争、身份或项目绑定不确定时停止且不创建替代中枢。
- 默认禁止替换可恢复的已登记中枢。唯一例外是用户在目标项目的新任务中明确授权“由当前任务替代登记中的 exact 旧中枢”；该流程只能按机器契约核对保存项目、原始 registry token、旧中枢精确 ID/可访问/不活动和当前任务真实 ID，并通过引擎 owner 锁与原子 registry CAS 完成，禁止手改 `hub.json` 或创建普通任务。
- 中枢替代 CAS 前旧登记仍权威，CAS 后新登记立即权威。锁保留 old/new ID、原始 token 和 owner 恢复证据；旧中枢按版本化退役标题、取消置顶、归档的顺序处理。只有三项退役结果都已确认，owner 才能带 replacement-retired 明确确认释放锁；中断、旧中枢退役失败或 task mutation 不完整时保留可恢复状态并停止，绝不创建第三个中枢。
- 任务管理不可用、创建失败、结果不可管理或身份不可确认时停止。禁止中枢回退执行；隐藏子代理不得替代用户可见任务。
- 一次性要求不成为长期授权；文档同步、提交、推送、外部操作和长期机制变更均需明确授权，但授权后仍由原执行任务继续。初始执行授权、文档草稿批准和最终完成验收互不替代；等待验收期间不得释放名额。

## 执行、替代与升级

- 执行任务持续承担同一请求，不因修改轮次、上下文长度、动作种类或范围确认自动轮换。任何替代、轮换或继任都必须由用户明确授权；授权只允许延续同一请求及已确认边界。替代时的前任归档属于恢复机制，不得当作用户验收归档。
- 需要明确替代时，原执行任务直接取得用户授权、固定安全检查点，并按协议处理精确前任和唯一继任；无真实 ID 时恢复原任务，queued 身份不得重复创建。继任重读规则、核对工作区，历史验证只算历史证据。
- 独立 worktree 仅在存在已授权可传递检查点时替代；缺少明确替代授权时停止并保留原任务。
- `$upgrade-project-flow` 只处理调用任务所属当前保存本地项目。身份或规范路径不匹配时，在读取或操作其他项目前停止。
- 工作流 plan、apply、resume 或 rollback 均由该获批请求唯一的可见任务完成；plan 后补充 apply 授权继续原任务。任务身份建立后，该任务自行维护 claim、屏障和事务；resume 只恢复已有 claim、屏障和原任务。中枢不再协调该升级请求。
- 升级始终穷尽普通、置顶和归档任务的分页元数据；历史只定向读取升级任务、活动快照任务及身份或状态有歧义的候选，元数据不完整或歧义未消除时才回退完整历史读取。
- apply、resume 或 rollback 在固定空快照前先发布 provisional 创建屏障；中枢每次物化执行任务前都须穷尽同项目任务元数据，并定向读取升级候选的原始屏障消息以证明不存在 provisional/active 屏障。看到同项目 provisional 或 active 屏障后不得物化任何新执行任务，只能排队。屏障不阻止既有任务继续完成和自归档；released 或 cancelled 后中枢才恢复创建。
- apply、resume 或 rollback 的文件事务开始前，除永久中枢和当前升级任务外，活动快照必须为空。发现任一 active、blocked、waiting、queued 或 `awaiting_acceptance` 任务时立即失败关闭：不归档活动任务、不创建继任、不执行文件事务，并保留原升级任务等待。
- 快照中的现有任务必须各自在原任务中完成并精确归档。其他占位任务全部释放后，用户继续原升级任务；该任务重新穷尽元数据并确认空快照后才可进入文件事务。
- 插件托管内容采用新版；“项目事实”和项目状态保留；未托管碰撞停止。事务成功后按已部署契约完成必要核对；失败保持屏障，禁止重复事务或角色回退。
- 证据、观察、截止和恢复均按统一协议及机器契约；未完成协调只报告待续。

## 项目状态

- `docs/PROJECT_STATE.md` 只记录当前目标、进展、重要结论和下一步，不提供授权或本轮验证证据。
- 仅在长期状态实质变化且文档同步获授权时使用 `$project-workflow-manager`。

## 交付文档

- Bootstrap 的 install/recovery 和 Upgrade 的 apply/resume/rollback 通过项目流引擎写入受管 Markdown 时属于部署例外，无需先提交 Markdown 草稿或取得逐文件草稿批准；部署请求本身的执行授权、冲突选择和最终验收仍按各自流程处理。
- 部署例外只覆盖引擎事务计划中的受管 Markdown 路径。普通任务修改 Markdown、部署任务额外修改非受管 Markdown，仍执行以下评审规则。
- 所有新建或修改的 `.md` 都必须由执行任务先在当前聊天中提交完整纯文本草稿和精确目标路径。
- 只有用户明确批准当前精确草稿后，执行任务才能写入 Markdown；含糊同意、对旧草稿的批准或最终任务验收都不能替代文档批准。
- 用户否决或修改草稿时，执行任务在当前任务内修订并重新提交，不返回中枢。草稿内容或目标路径发生变化，已有批准立即失效。
- 文档评审、Markdown 写入和后续修改全部留在原执行任务中，不创建第二个任务。写入后再次修改同一文档时重新进入评审流程。
- 从纯文本转换为 Markdown 时只能增加必要结构和格式，不得改变未经批准的实质内容。
- 获批文档不得创建独立封面或单独标题页，正文首个非空标题必须是 `#`，后续标题按层级递进；执行任务只校验本次新建或更新的文档，不以此授权扫描或改写其他文件。
